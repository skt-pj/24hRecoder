# Memoket Gem v0.7.105 / official-HCI design (reviewed)

Scope: user START → user STOP → 01 response → one matching latest recording → DATA/CRC/durable save → named 05 → 0501 → read-only 00. The state flow is notification-driven; neither GATT write success nor a timer is an application protocol ACK.

Source: user-supplied `capture_output_appli(1).zip/capture_output_appli/btsnoop_hci.log`, 2026-10-10 22:49 JST (8,520 HCI records); project Wiki 04 §§13–22. Audit against source, not inference:

| event | observed ATT flow |
|---|---|
| handshake | 00/0000, 2701/2702, e1/e13a02, f300/f30000, e301/e3…, ff68/ff68…, e5/e501, e8/e8… |
| first 03 | 22:49:34.927 03 → 22:49:35.020 03ff |
| DATA CCCD | 0000 write ACK → 0100 write ACK |
| 01 | 010000 → 010101 + 20261010_224936_2.opus (starts sending audio, NOT a harmless full listing) |
| DATA and intermediate | seq0..43, 44×480B=21120B; 00→00010002+filename, then e1→e13a02 |
| 02 | 0200→0200010005 + filename + 00005280 + b3211feb; CRC32 verified |
| finalize | 03→030100000516 + filename + 00005280 → 03ff |
| named delete | 05 + 0x16 + filename → 0501 |
| after delete | 00→0000; NEVER reissue 01 to confirm disappearance |

Stop only if THIS running service accepted START 03ff on the SAME live authenticated GATT; persisted `録音中` and `00 01` cannot authorize STOP because 00 01 occurs in transfer. Fail closed on disconnect, missing START, CCCD mismatch, unexpected status, metadata filename/size/CRC mismatch, 0301 structural mismatch, 03ff without 0301, or persistence failure. Do not send 05 before CRC and durable file save. No automatic full-file loop, no fixed trial recording seconds, no new transfer after 0501.

Selection limit: the observed 01 returns ONE file and starts its DATA. It does NOT prove complete list ordering or latest-first behavior. Only accept a filename matching the app's own recording start/stop window (and any known current filename hint); otherwise fail with NO 05. This is best-effort latest selection, not proof of ordering across multiple pending files.

Evidence boundary: 03ff is an opcode ACK, not physical STOP proof. 0501 is a deletion request ACK, not independent Gem flash readback. 0000 means idle only. Report the three facts separately and leave LED/actual file disappearance for device acceptance.

Review (before implementation):
- Critical: previously re-issued 01 after 0501, causing new DATA stream → remove.
- Critical: previously allowed STOP on reconnect based on persisted state and 00 01 → prohibit.
- Critical: previously trusted 03ff before verifying 0301 filename/size → strict two-stage validation.
- High: previously accepted malformed 02/03 framing and 0501 with extra bytes → strict captured forms.
- High: intermediate 00/e1 accepted unrelated payload → compare exact target filename / response.
- High: 0000 after 0501 counted as verified deletion → no physical-deletion claim.
- Unresolved: official raw trace does not prove exact physical STOP opcode, multi-file latest sorting, or flash deletion. Never claim these are verified.

Acceptance: automated JUnit tests passing, signed APK/monotonic version validated, explicit real-Gem LED/audio file deletion verification still required.
